# transformation-core/.../transformation/core/deferred — agent notes

Makes parallel rule bodies safe against EMF's non-thread-safe write path: instead of mutating the model, a rule mutates a JDK dynamic proxy that records the write as an immutable operation record; the executor replays the queue single-threaded, sequence-ordered, at a barrier. Two independent layers live here — the FULL deferral layer (`DeferredEObject` + `EMFOperation` + `OperationQueue` + `DeferredEList`, defers every write) and the CONTAINMENT-ONLY layer (`ContainmentDeferringProxy` + `ContainmentOp`, defers only containment mutations and lets attributes through). Enable via `TransformationContext.enableDeferredWrites()` / `enableDeferredContainment()` respectively.

Every write path here has one shared hazard: a queued operation is only visible in the real model AFTER commit, and an uncommitted queue means silently lost writes.

| File | Purpose |
|---|---|
| `ContainmentDeferringProxy.java` | `InvocationHandler` deferring ONLY containment mutations, so attribute writes stay immediate and cheap. Exports `createProxy(T delegate, TransformationContext ctx)`, `unwrap(T)`, `hasContainmentFeatures(EClass)`, `invoke(...)`, nested `ProxyMarker` and `DeferredContainmentEList` (implements `EList<EObject>` with `add`, `addAll`, `set`, `remove`, `removeAll`, `retainAll`, `clear`, `move`). Intercepts `setXxx(child)` and `eSet(feature, value)` on single-valued containment `EReference`s (→ `ContainmentOp.SetReference`) and `getXxxList()`/`eGet` on many-valued containment (→ a `DeferredContainmentEList` queueing `add`). Everything else — attributes, non-containment references, `eContainer`/`eResource` and the rest of the EMF lifecycle — passes straight through. Read-after-write holds for single-valued containment: `setIcon(icon)` then `getIcon()` returns the pending value before commit. Three static `ConcurrentHashMap` caches (`(EClass,Method)`→`MethodKind`, `(EClass,Method)`→`EReference`, `EClass`→has-containment, plus a proxy-interface array cache) are JVM-global and never evicted — long-lived processes accumulate one entry per distinct `(EClass, Method)`. `hasContainmentFeatures` returning false is the skip signal: attribute-only types are not proxied at all, so callers must not assume every target is a proxy. `unwrap` before handing an object to code that reads the delegate directly (`EcoreUtil.copy`, serialisation). |
| `ContainmentOp.java` | `sealed interface` of the containment-only operation records, permitting exactly `AddToList`, `SetReference`, `MoveInList`. Exports `long sequence()` and `void apply()`, implemented by each record. `AddToList(parent, feature, child, sequence)` replays `parent.eGet(feature).add(child)`; `SetReference(parent, feature, child, sequence)` replays `parent.eSet(feature, child)`; `MoveInList(parent, feature, newPosition, object, oldPosition, sequence)` replays `list.move(...)` using the object variant when `object != null`, else the positional variant with `oldPosition`. `MoveInList` MUST be applied after every `AddToList` or the target index is out of range — sequence numbers are assigned so moves sort last. Being sealed, adding a fourth op kind requires editing the `permits` clause. |
| `DeferredEList.java` | `EList<E>` wrapper giving the full-deferral layer read-after-write consistency on list features. Exports ctor `(EList<E> delegate, EObject container, EStructuralFeature feature, OperationQueue queue)`, the mutators `add`/`addAll`/`remove`/`removeAll`/`retainAll`/`clear`/`set`/`move` (each records an `EMFOperation` and mutates only pending state), the readers `size`/`isEmpty`/`contains`/`containsAll`/`get`/`indexOf`/`lastIndexOf`/`toArray`/`iterator`/`listIterator`/`subList` (which return delegate PLUS `pendingAdditions` minus `pendingRemovals`), and `clearPendingState()`. Elements are `unwrap`ped before queueing, so the recorded op targets the real EObject, not a proxy. `pendingAdditions` is a `Collections.synchronizedList(ArrayList)` deliberately NOT a `CopyOnWriteArrayList` — CoW is O(N²) for N additions and destroyed parallel-transformation throughput; the consequence is that iterating a read view while another thread adds needs external synchronisation. `pendingRemovals` is an identity-based `ConcurrentHashMap.newKeySet()`. `clearPendingState()` must run after commit or reads double-count committed elements. |
| `DeferredEObject.java` | `InvocationHandler` for the FULL-deferral proxy — every setter and list accessor is captured. Exports `createProxy(T delegate, OperationQueue queue)`, `unwrap(T)`, `unwrapWithPendingValues(T)`, `clearPendingStateIfProxy(Object)`, `invoke(...)`, and nested `interface ProxyMarker { EObject getDelegate(); void applyPendingValues(); void clearPendingState(); }`. `setXxx` records `SetAttributeOp`/`SetReferenceOp`, `getXxxList()` returns a memoised `DeferredEList`, `eSet` records the matching op, `eUnset` records `UnsetFeatureOp`. Pending single-valued writes are tracked per feature in a `ConcurrentHashMap`, so `setName("Orders")` then `getName()` returns `"Orders"` rather than null. `PASSTHROUGH_METHODS` (`equals`, `hashCode`, `toString`, `getClass`, `eClass`, `eResource`, `eContainer`, `eContainingFeature`, `eContainmentFeature`, `eContents`, `eCrossReferences`, `eAllContents`, `eIsProxy`, `eAdapters`) always hit the delegate — `eContents` therefore does NOT show pending children. Anything reading the delegate directly (`EcoreUtil.copy`, XMI save) needs `applyPendingValues()`/`unwrapWithPendingValues` first, and `applyPendingValues` flushes SINGLE-VALUED features only — list ops still require an `OperationQueue.commit()`. |
| `EMFOperation.java` | `sealed interface` of the full-deferral operation records, permitting `SetAttributeOp`, `SetReferenceOp`, `UnsetFeatureOp`, `AddToListOp`, `AddAllToListOp`, `RemoveFromListOp`, `RemoveAllFromListOp`, `ClearListOp`, `SetListElementOp`, `MoveListElementOp`. Exports `long sequence()`, `void apply()`, `EObject target()`, `EStructuralFeature feature()` — every record supplies all four so the queue can order, replay and attribute a failure. Records are immutable and captured during the parallel phase, replayed sequence-sorted single-threaded at commit, which is what removes the need to lock EMF objects. Values are already unwrapped at QUEUE time (in `DeferredEObject.handleSet`), so `apply()` must never see a proxy. Adding a new op kind means editing the `permits` clause. |
| `OperationQueue.java` | Thread-safe collector and single-threaded replayer of `EMFOperation`s. Exports `enableDeferredMode()`, `disableDeferredMode()`, `isDeferredMode()`, `nextSequence()`, `add(EMFOperation)`, `size()`, `isEmpty()`, `commit()`, `clear()`, `reset()`, `getOperations()`. Backed by a `ConcurrentLinkedQueue` plus an `AtomicLong` sequence counter; `deferredMode` is a `volatile boolean` defaulting to FALSE — with it off, `add(op)` APPLIES the operation immediately instead of queueing, so forgetting `enableDeferredMode()` silently reverts to unsafe direct writes. `commit()` DRAINS the queue by polling, sorts by `sequence()`, applies in order, returns the applied count, and on the first failure logs the op class and sequence then rethrows wrapped in `RuntimeException` — leaving the already-applied prefix in the model and the un-applied suffix already polled off the queue, i.e. commit is NOT atomic and not resumable. `commit()` on an empty queue returns 0 without work. Reachable from rule code via `TransformationContext.getOperationQueue()`. |
