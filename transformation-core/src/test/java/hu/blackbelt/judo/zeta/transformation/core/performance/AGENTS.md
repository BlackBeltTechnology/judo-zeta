# transformation-core/src/test/.../transformation/core/performance — agent notes

Throughput harness for `TransformationExecutor`. Excluded from `mvn test`; runs only under the `performance` Maven profile. Full suite takes ~15–30 minutes.

| File | Purpose |
|---|---|
| `BenchmarkRules.java` | The `@TransformationContext` rule set the benchmark transforms with — ECore→ECore so no metamodel dependency skews the numbers. Exports `createPackage`, `createClass`, `createClassGuarded` (`@Guard` on `checkGuard`), `createAttribute`, `createReference`, `createOperation`, plus nested `GuardRejector` implementing `evaluate` to reject a configurable fraction of elements. Rules carry `@TransformRule`, `@Transform`, `@To`, `@Greedy`, `@Lazy` so both eager and lazy paths and both matching semantics are measured. Rejection rate is driven by `SyntheticModelGenerator.Builder.guardRejectionRate` — changing a rule's annotations changes what the published numbers mean, so treat this file as part of the benchmark's calibration, not as ordinary test code. |
| `README.md` | Operator guide for the benchmark suite. Documents the invocation (`mvn test -Pperformance -Dtest=ZetaPerformanceBenchmark`, `\$NestedClass` to target one suite), the reported metrics (median/p50 across 5 measured iterations, IQR `[p25, p75]`, throughput/sec, heap delta, cache hit rate), the CSV artefacts written to `target/benchmark-results/` (`{benchmarkId}-raw.csv`, `{benchmarkId}-summary.csv`), the baseline workflow (copy a summary CSV to `baseline.csv`; later runs FAIL on regression beyond 20%), the parameter matrix (model size 1K/10K/50K/100K, parallel true/false, `ELEMENT_BY_ELEMENT` vs `RULE_BY_RULE`, chunk size 10/100/500/1000, threads 1/2/4/8), and the fixed-heap advice (`-DargLine="-Xmx4G"`). States the limits explicitly: results are hardware-dependent, so trend analysis is valid only on one machine. Contains a stray CJK fragment in the baseline sample output. |
| `SyntheticModelGenerator.java` | Generates a reproducible ECore model of a chosen size so benchmark runs are comparable. Exports `generate()`, `getResourceSet()`, `getTotalElementCount()`, nested `enum ReferencePattern`, and a `Builder` with `packageCount`, `classesPerPackage`, `attributesPerClass`, `referencesPerClass`, `operationsPerClass`, `randomSeed`, `guardRejectionRate`, `referencePattern`, `sharedTypes`, `typeDistribution`, `build`. `randomSeed` is the determinism contract — omit or change it and successive runs are not comparable and a regression check is meaningless. `guardRejectionRate` and `referencePattern` shape how much work rules actually do, so they must be held constant when comparing against `baseline.csv`. `getTotalElementCount()` is the denominator for reported throughput. |
| `ZetaPerformanceBenchmark.java` | The benchmark itself: builds a synthetic model, runs `TransformationExecutor` under a `BenchmarkConfig`, aggregates timings and writes the CSVs. `@Tag("performance")` (that tag is what excludes it from normal runs) and `@DisplayName("Zeta Performance Benchmarks")`, package-private, with `@BeforeEach setUp`. `@Nested` suites: `SmallModelBenchmarks` (1K: sequential EBE, parallel EBE, parallel RBR), `MediumModelBenchmarks` (10K, same three), `ChunkSizeBenchmarks` (10/100/500/1000 at 10K parallel), `ThreadCountBenchmarks` (1/2/4/8 at 10K). Runs `WARMUP_ITERATIONS` = 3 discarded passes then `MEASURED_ITERATIONS` = 5 recorded ones and reports the MEDIAN — a single-iteration change invalidates comparability with stored baselines. Also defines a local `ModelProvider` (`getAllContents`) so the harness needs no metamodel module. Add a suite by adding a `@Nested` class that builds a `BenchmarkConfig(size, parallel, ExecutionStrategy, chunkSize, threads)` and calls `runBenchmark(id, config)`. |
